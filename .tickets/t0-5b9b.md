# Decide the purpose of the pendingOffline resume flag: build its reader and clearing rule, or delete it

Split from boo-zyx1, which left the Dart code unchanged. Found by reading code on November 12 (main at 87d20f45). Nothing was run.

What the code does. Playback._save (lib/playback/playback.dart, about line 1693) writes pendingOffline on a listening resume record. The value is true when the network is disconnected or unknown at the save, or when the record already holds true. The only production reader is the getter Playback.pendingOfflineResume (about line 763), and its only production caller is _save itself. So nothing acts on the flag, and no rule clears it: once true, it stays true in every later save of that record. Decoding does not need the key (playback.dart, about line 1160). Two tests read the getter: test/playback/playback_test.dart:231 and test/playback/replacement_test.dart:484.

What the plans say. docs/plans/bookfin.md, section Standard Jellyfin behavior: "Keep pending offline progress locally. Reconcile it with newer server activity before uploading." docs/playback.md, section Durable local resume: "pendingOfflineResume says that the selected edition has retained local activity from a disconnected or unknown network. It is not a proof that other activity reached Jellyfin. Live reporting does not clear this flag or reconcile the record with another device." So the plan gives a purpose to the idea that the flag marks: a place that the user reached offline and that standard Jellyfin progress did not receive. No code builds that purpose. LiveReports (lib/playback/reporting.dart) sends progress only while the book plays on Wi-Fi or mobile data, and nothing uploads an offline place after the network returns. The record journal (lib/sync/journal.dart) tracks uploads to the Bookfin Storage plugin, not to standard Jellyfin progress.

The decision is the user's. Design A: build the purpose. After the network returns, reconcile a flagged resume with the newer Jellyfin position, upload it, and clear the flag. It costs a new upload path with a conflict rule, and it gives accounts without the plugin their offline progress in Jellyfin. Design B: delete the flag and the getter, keep decoding tolerant of old records, and change the plan sentence to say that the record journal is the one owner of pending progress. It costs nothing to build, and offline progress then reaches standard Jellyfin progress only when the book next plays online.
