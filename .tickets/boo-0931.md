# Restore the record journal at launch without replaying every saved action

Found in the code survey of November 12 (main at f9f26500). Nothing was run for this finding. Status: confirmed code path, estimated scale. Playback saves one resume action for each media-second (lib/playback/playback.dart:1370). At launch, `_readRows` (lib/playback/store.dart:1535) decodes every stored action, and `RecordJournal.receive` (lib/sync/journal.dart:209) copies, validates and keeps each one in memory. Ticket t6-t9po measured about 20 microseconds for each action on the Mac. One month at 2 hours a day is about 216,000 actions, so the restored book and position wait for seconds, and the heap holds every action. Keep every action on disk, as the November 3 decision says. Restore from the rows that the same transaction already writes (record_versions, record_coverage, pending, cursor), and read a retained action from SQLite only when an operation needs it. Keep the full replay for the invariant checker and for salvage.

### Result and ownership

SQLite remains the complete immutable-action authority. Ordinary native restoration reads current identities, causal coverage, pending identities, cursor and required current/held payloads. Superseded payloads remain byte-for-byte on disk and are read only when an operation needs them. Full replay remains explicit for invariants and repair; preferences/web retain their existing whole-value behavior. There is no action-format change, plugin change, expiry, compaction, coalescing or journal-checkpoint protocol.

LocalResumeStore still serializes the entire read/change/transaction/cache transition. RecordJournal owns current versions, causal waiting, pending acknowledgments and local action creation. Native journals release superseded payloads after successful commits. The owner retrieves originals for immutable duplicates, preserved conflicts, pending uploads, the last local action (including remote supersession), kept-copy recovery and server-copy repair. Transport grouping/confirmations and sync scheduling are unchanged.

Schema four adds derived author/sequence/record lookup columns and indexes. The upgrade decodes batches of 256 in workers inside SQLite's upgrade transaction, changes no original payload bytes, and rolls back on failure. The explicit full checker verifies lookup columns against payloads as well as independently replaying actions and comparing committed/current/pending/coverage state. Read-only restoration uses one SQLite snapshot; bounded owner-connection fallback keeps payload decoding in workers. Contract failures propagate.
