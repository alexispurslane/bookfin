# Upload and receive personal records in batches

Found in the code survey of November 12 (main at f9f26500). Nothing was run for this finding. Status: confirmed. lib/playback/store.dart:458-489 sends one HTTP PUT and one local SQLite transaction for each pending action, oldest first. The plugin refuses a discovery page above 4 objects (plugin/Bookfin.Storage/StorageController.cs:24-27), and the client stops after 128 pages. One hour of listening queues about 3,600 actions. The next sync then makes 3,600 round trips in sequence, and the newest place arrives last. A receiving device takes at most 512 actions for each sync, and each cut-off sync reports "Sync did not finish". Step 1 needs no plugin change: upload with bounded concurrency and acknowledge each batch in one transaction. Step 2 changes the plugin API (a batch PUT and larger discovery pages, selected by plugin version). The November 3 decision in t6-t9po kept that API fixed, so step 2 needs a user decision.

## Step 2: additive v2 batch protocol

Version selection uses the loaded plugin assembly version in a valid authenticated v1 discovery reply. Missing version on a valid old page selects legacy mode; a supported 0.x minor of at least 2 selects v2. Invalid/future-major versions, authentication, network and corrupt-response failures do not silently fall back. The complete contract is documented in `plugin/Bookfin.Storage/README.md` for independent callers.

V2 uses 256-object/1 MiB payload groups and discovery pages. The plugin validates the complete batch before mutation and commits successful items in one ObjectStore transaction, using the same immutable-object mutation operation as single PUT. Per-item conflicts/deletions retain existing semantics. Transport validates confirmations by identity, not response order. Missing, duplicate or mismatched confirmations retain their pending identities; unexpected identities or interrupted responses retain the whole group. Group acknowledgment and page/cursor atomicity stay in LocalResumeStore. Event scheduling remains unchanged. Wire encoding, confirmation validation and discovery parsing use worker hops; native HTTP request encoding also uses a worker. Existing journal admission/storage JSON work is separately tracked in te-6j4k, linked with t4-kdc8; no broad journal ownership refactor or startup restoration was added.
